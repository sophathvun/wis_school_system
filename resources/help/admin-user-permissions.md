## Before you start

Open **Administrator → Roles & Permissions → Users** with permission to manage access settings. User-specific grants supplement shared role and department access.

## Find and open the user

Search or filter the Users list, then open the intended user's permission-assignment area. Verify name, username, and campus details before making changes.

## Read inherited permissions

The tree shows inherited access with source labels such as **Role** or **Department**. Inherited controls may be locked because their source must be changed at the role or department level.

An inherited ON state is not necessarily a separate user-specific grant. Saving the user should not be treated as copying all inherited permissions permanently onto that account.

## Add a user-specific permission

1. Review the inherited sources and intended campus assignment.
2. Find the required main menu, submenu, or action.
3. Enable the additional permission where allowed.
4. Keep the required parent permissions enabled through an inherited or direct source.
5. Choose **Save User Permissions**.

For a non-global account, review the campus selection as well as the action switches. A permission without the appropriate campus context may not allow the intended record operation.

## Remove or change access

Identify the source first. Turning off a direct grant does not remove the same permission inherited from a role or department. Change the appropriate shared source only after reviewing its impact on other users.

Some modules apply additional restrictions, including assigned-session access, explicit denials, or separate action and tab permissions. Verify the exact feature after saving.

## Troubleshoot inherited controls

If an inherited switch cannot be changed, inspect its source rather than enabling Full Access. If the permission appears ON but access is denied, check parent permissions, campus scope, role status, and module-specific requirements.
